# 测试版发布前 GM 功能检查报告

检查日期：2026-10-18
范围：后端 `apps/api`。共两件事：(1) 后端能否正确解析并应用模型返回；(2) 提示词和契约有没有讲清楚每项功能的作用、用法、返回格式和数值怎么改。本次只检查，不改代码。

## 检查方法

- 通读以下文件：输出契约 `content/output_contract.txt`、`content/gm_turn.schema.json`；故事弧契约 `content/story_arc_contract.txt`、`content/story_arc.schema.json`；提示词组装 `content_registry.py`（`build_messages`、各 `RUNTIME_*_POLICY`）；解析与裁决 `narrative_contract.py`；落库 `story_repository.py`；模型调用 `model_provider.py`；任务调度与重试 `server.py:515-607`；作为规则原文注入的 5 份设定文档。
- 用脚本直接调用 `narrative_contract._evidence_authorizes_action` 和 `model_provider._model_json_object`，验证突破、任务授权和 JSON 提取在常见输入下的表现（结果见 B1、L6）。
- 以只读方式查询本地库 `apps/api/.data/fantasy_simulator.sqlite3` 中的 5 个冻结内容修订。它们的 gm_turn schema 字段集合完全一致。现有那 1 个存档所冻结的 `output_contract.txt` 里没有“长期记忆证据规则更新”那一行（见 M3）。
- 后端测试：`runtime/python/python.exe -m unittest discover -s apps/api/tests` 共 186 项，只有已知的 `test_gm_writing_context` 1 项失败，与基线一致。

### 通用机制（所有功能都适用）

- 模型返回先经过 `_model_json_object` 提取 JSON（`model_provider.py:211`）。接着按存档冻结的 schema 校验（`contract_registry.py:57`），再做 `validate_gm_response` 逐字段检查，最后由 `adjudicate` 裁决。
- 任一步抛出 `ContractError` 后，系统会把错误位置附在提示里自动重试 **1 次**（`server.py:555-588`）；两次都失败时，任务以 `MODEL_OUTPUT_FORMAT` 失败（不可重试）。落库在同一个事务里完成，失败时整体回滚，不会写入一半。
- 所有非空的 `evidence` 都必须是 `narrative.body` 的**逐字子串**（`narrative_contract.py:711-714`）。

## 二、问题清单（按优先级）

### 阻断发布

**B1. 突破和普通任务“接受”的授权判定依赖隐藏的关键词表，加上“完整分句”的硬性要求，常见说法都会被拒**
- 位置：
  - 关键词表：`apps/api/narrative_contract.py:106-110`（`GENERIC_TASK_ACCEPT_TERMS`、`BREAKTHROUGH_ACCEPT_TERMS`）
  - 判定逻辑：`narrative_contract.py:285-292`（`_evidence_authorizes_action` 要求 evidence 与玩家输入中**以标点切分出的某个完整分句完全相等**）
  - 调用点：`:295-301`（突破）、`:1033-1037`（新建 active）、`:1078-1083`（转为 active）
  - 契约：`content/output_contract.txt:3`（只写了“逐字引用本次有效玩家输入”）、`content_registry.py:495`
- 实测结果（`_evidence_authorizes_action`）：
  - `我要突破到六阶`、`我闭关冲击六阶`、`准备突破瓶颈` → 拒绝。`突破` 本身不在关键词表里，只有 `尝试突破/进行突破/开始突破/升阶/晋阶/冲阶/冲关/破境…` 才算
  - 玩家输入 `我盘膝坐下，尝试突破到五阶`：模型引用整句 → 拒绝；只引用 `尝试突破到五阶` 才能通过
  - `这个委托我接了`、`我帮你找回项链`、`我答应帮她寻找潮音珠` → 拒绝；`我接受这个任务` → 通过
- 影响：突破是核心成长路线，任务栏依赖任务进入 active。玩家用自然说法时，模型按契约给出的提案会被整回合拒绝。重试提示也不说明关键词要求，第二次大概率仍然失败，任务最终报“自动修正重试后回复仍不合法”。另一种情况是模型退而不提交提案，但正文已经写了“突破成功”或“接下委托”，正文与权威状态就会不一致。
- 建议修法：
  1. 放宽判定：evidence 只要是玩家输入的逐字子串、且所在分句不含否定即可通过，不再要求与整个分句完全相等。
  2. 扩充关键词：突破类加入 `突破`、`冲击`、`闭关`；接受类加入 `接了`、`答应`、`同意帮`、`我来办`、`交给我` 等，并保留否定检测。
  3. 在 `RUNTIME_ADJUDICATION_POLICY` 中明确告诉模型：action_evidence 应当摘取玩家输入里**表达接受或突破意图的那一个短分句**，不要整段复制；没有明确意图时保持 offered，突破则只描写准备过程。
  4. 补充回归测试，覆盖上面列出的常见说法。

### 高

**H1. 羁绊和声望的影响等级上限从没告诉模型，schema 范围又与实际上限矛盾**
- 位置：上限定义在 `narrative_contract.py:1158-1159`（羁绊 5/15/25/35）和 `:1176-1177`（声望 5/15/35/50）；前置校验 `:525`（羁绊 ±35）、`:538`（声望 ±50）；schema `content/gm_turn.schema.json:264`（±50）、`:277`（±100）；契约 `output_contract.txt:3` 只写了“变化幅度不得超过该影响等级”；`声望与羁绊系统.md` 没有任何数值。
- 影响：模型只能猜每档上限，major 事件给羁绊 +30 就会整回合被拒。重试提示是“羁绊变化幅度超过事件影响等级”，同样不带数字。major 这一档在羁绊里是 25、在声望里是 35，更容易记混。另外，schema 越界与校验越界报出的错误文案不同（“必须是有效整数”），排查也困难。
- 建议修法：在契约或运行时策略里明确写出两张表（含正负号），把 schema 的 maximum 改成与后端一致（羁绊 35、声望 50），并在报错信息里带上该等级的允许上限。

**H2. 故事弧自动总结失败一次后会永久停止**
- 位置：`story_repository.py:959-967`。自动模式会按指纹查找同一批来源的历史任务，**不论其状态**（包括 failed）都直接返回 `created=False`。`:942-953` 每次都选择第一批未覆盖的 25 个连续节点，所以永远命中同一批。前端只有合并入口（`GameWorkspace.tsx:127`），`api.createStoryArc` 没有任何调用点。
- 影响：故事弧任务强制开启思考，容易超时。只要某次超时、契约失败或被取消，这个存档就再也不会自动生成故事弧。较早的节点会一直以摘要形式全部塞进上下文，上下文持续膨胀，最终可能超出模型上限，长期叙事的连续性也会变差。
- 建议修法：自动模式只复用 `queued/running/succeeded` 状态的任务；对 `failed/cancelled/stale/interrupted` 允许重新创建，可加入失败次数或退避上限。同时在记忆面板提供“重新整理故事弧”按钮，接上 `createStoryArc`。

**H3. 短期资源上限永远冻结在建卡时的数值**
- 位置：`story_repository.py:56` 只在建卡时拷贝一次 resources。`narrative_contract.py:855-861` 只修改 `current`；`:961-966` 升阶时更新了 exp 和 base_power，没有更新资源上限；`:895-907` 体质变化也不影响上限。`短期与长期属性设计.md:18,29,93` 却明确写着上限受等阶和体质影响。
- 影响：1 阶起步的角色升到 5 阶后，HP/MP/SP/ST 上限仍是 1 阶时的数值，和战力、文档都对不上。模型知道上限“应该”变大，却没有任何字段可以表达。
- 建议修法（二选一）：
  - 由程序在升阶时按阶位或种族规则重算上限，可沿用建卡时的计算方式乘以阶位系数；
  - 在 resources 提案中增加 `max_delta`，并设单回合上限，同时在契约里说明只在升阶或长期体质变化时使用。

**H4. 6 阶及以上满 EXP 时必须同回合创建突破任务，但提示词没写，而且失败或拒绝后会被反复强制创建**
- 位置：`narrative_contract.py:920-931`。契约 `output_contract.txt:3` 没有提到 `quest_kind=breakthrough`、`target_rank=rank+1`、`status` 只能是 `offered/active`（`:1038-1041`），也没提这是硬性要求。
- 影响：EXP 刚满的那一回合，如果模型没有顺手创建突破任务，整回合会被拒。另外，只要当前没有处于 `offered/active/completed` 状态的突破任务（例如玩家拒绝了、任务失败了），之后**每一回合**都会被强制再建一个。这与 `经验值功能设定.md:213`“不得无限生成新的突破任务”相违背，也会打断与突破无关的日常回合。
- 建议修法：在契约中写明创建规则和字段取值。后端不要再整回合拒绝，可改为两种方式之一：
  - 由程序生成一条 `eligible` 状态的占位突破任务；
  - 只在 warnings 里提示。
  已 declined/failed 的情况，交给玩家主动发起。

**H5. 角色死亡后没有任何结束或复活流程**
- 位置：`story_repository.py:186-257` 的 `create_job` 和 `:901` 的 `can_act` 都没有检查 `alive`；`narrative_contract.py:723-725` 拒绝死者 HP 变为正数；契约 `output_contract.txt:3` 写的是“已死亡角色不能靠**普通** HP 恢复自动复活”。
- 影响：死亡后玩家仍能继续提交行动，模型却没有任何指引（该写尸体视角、旁观者视角，还是结局？），每回合只能返回 dead 加 HP 0，体验很怪。契约暗示“非普通手段”可以复活，后端却拒绝任何复活，模型若按契约写复活，整回合会被拒。
- 建议修法：明确产品规则，例如死亡即进入结局，只允许重塑最新节点或读档。后端在 `create_job` 中对 `turn/intervene` 返回 `CHARACTER_DEAD`，前端显示结局状态并提供重塑入口。如果要保留复活，就增加一个受正典例外约束的 `revive` 提案，并修改契约措辞。

### 中

**M1. 天赋和技能完全没有使用说明，后端校验也偏松**
- 位置：契约和全部规则文档中都搜不到“天赋/技能/talent/skill”。schema 中的定义见 `gm_turn.schema.json:284`（`learnable`）。后端见 `narrative_contract.py:545-553`（`update/remove` 不要求 id）和 `:1192-1209`。初始天赋为 `talent.legacy`（`story_repository.py:63-64`），而 `identity.talent` 中的原文不会同步更新。
- 影响：模型不知道两者的区别：天赋是先天、极少变化的；技能是习得的，与 EXP 和学习挂钩。它也不知道什么情况下应该新增技能、是否允许删除玩家的初始天赋、id 应该怎么填。结果可能是滥发技能、从不发技能，或误删初始天赋。`update/remove` 不给 id 时，报错是含糊的“skills 不存在”。
- 建议修法：
  1. 新增一段运行时策略，讲清天赋和技能的语义、获得门槛、命名粒度；写明 add 时 id 填 null，update/remove 必须用 `authoritative_state` 中已有的 id。
  2. 禁止模型删除 `talent.legacy`，或要求 remove 必须有正典依据。
  3. 在 validator 中要求 `update/remove` 提供 id，与 conditions 的处理保持一致（`:430-431`）。

**M2. 年龄完全是静态的**
- 位置：年龄只在建卡时设定（`catalog.py:752-769`）；schema 中没有对应字段；`narrative_contract.py:825` 只累加 `elapsed_minutes`。
- 影响：时间跳跃（例如在学院学习三年）后年龄不变；长寿种族与短寿种族在时间流逝上也没有任何区别。
- 建议修法：最简单的做法是由程序根据累计的 `elapsed_minutes` 推导“当前年龄 = 初始年龄 + 经过年数”，写入 `authoritative_state` 供模型参考，无需新增提案字段。如果需要剧情改龄（例如返老还童），再增加受限提案。

**M3. 长期记忆证据规则在同一份契约内自相矛盾**
- 位置：`output_contract.txt` 第 2 行写明旧规则“不再适用”，但第 3 行末尾仍完整保留“至少 8 个字符……逐字等于完整分句……facts/unresolved 每项必须与 evidence 完全相同”。`content_registry.py:514` 的运行时策略与 schema 的 description 都说不要求逐字。后端（`narrative_contract.py:580-598`）实际并不校验逐字。现有那 1 个存档冻结的修订（`content-v2-99ba13…`）中没有第 2 行，只有旧规则。
- 影响：模型会把 facts/unresolved 写成与 evidence 完全相同的原文片段，记忆质量下降，也浪费输出 token。
- 建议修法：从当前 `output_contract.txt:3` 中删掉旧规则那一段。对老存档，在 `RUNTIME_LONG_TERM_MEMORY_POLICY` 中加一句“若契约原文与本策略冲突，以本策略为准”。这项策略本来就对所有存档生效。

**M4. 记忆的 people/locations 填了人名或地名会导致整回合被拒**
- 位置：`narrative_contract.py:1286-1296`；schema description 见 `gm_turn.schema.json:331`（只提到权威状态和 new_npcs，漏了 canonical_npc_catalog）。
- 影响：这只是一个辅助字段，模型很容易写成“露米娅”这样的名字，却会导致整段叙事和全部状态变更一起作废。
- 建议修法：程序把无法识别的条目按名称映射成 ID，或直接丢弃并在 warnings 中记录，不要抛出 `ContractError`。同时让 schema description 与契约措辞保持一致。

**M5. 长期属性单回合允许 ±35，与“缓慢成长”的规则冲突**
- 位置：`gm_turn.schema.json:160`（±35）；`narrative_contract.py:421`（±100）、`:895-907`；`短期与长期属性设计.md:79,174`。
- 影响：单次事件就可能让体质 +35，属性曲线失控；后端只校验结果在 1..100 内。
- 建议修法：单回合正向变化最多 +2（重大伤残等负向变化可以放宽）；在契约中写明“通常 ±1，有长期积累才 +2”；validator 和 schema 改为同一个数值。

**M6. 装备 40% 在契约里是“参考”，在后端却是硬性上限**
- 位置：`output_contract.txt:3` 写的是“遵守常规装备约40%参考”；`narrative_contract.py:1223-1228` 对所有已装备普通装备的**总和**做硬性校验。
- 影响：模型给出一件看似合理的装备，可能因为它和已有装备的总和超标而导致整回合被拒，模型也算不出还剩多少余量。
- 建议修法：在 `authoritative_state` 中直接提供 `ordinary_equipment_power_cap` 和剩余余量；契约措辞改为“硬性上限：已装备 ordinary 装备 power 总和 ≤ 基础战力×40%”。也可以改成：超出部分不计入有效战力，并写入 warning，不再拒绝整回合。

**M7. 战力修正：临时修正不会过期，severity 与数值无关**
- 位置：`narrative_contract.py:1229-1279`；契约写的是“空数组表示保持既有修正不变”。
- 影响：伤势修正 −300 如果模型忘了移除，就会永久压低有效战力。“minor”档的正向修正在两阶差以内不限大小（例如 5 阶 +1500 也能通过）。
- 建议修法：
  - 在契约中写明“伤势痊愈、离开对应环境、强化结束时必须 remove/expire 对应的 temporary 修正”；
  - 为各 severity 设置数值上限，例如占基础战力的 10/25/50/100%；
  - 可选：对 temporary 修正设定按回合数或时间自动过期。

**M8. 故事弧提示词未限定来源范围、没有长度引导，压缩只能手动进行**
- 位置：`content_registry.py:175-193`（策略只说“来源内容”）；故事弧任务的上下文同时包含 `recent_full_turns`、`story_arcs`、`long_term_memories` 和 `current_action.frozen_sources`（`server.py:525-536`）；schema 允许 summary 长达 20000 字（`story_arc.schema.json:11`）。
- 影响：模型可能把来源以外的最近 10 个节点或其他故事弧写进本弧，造成重复和时间线错乱。summary 没有长度约束，再加上只能手动压缩，几百个节点后上下文会明显膨胀。
- 建议修法：
  1. 在策略中写明“只总结 current_action.frozen_sources，其余上下文仅供理解，不得写入”，并给出 summary 字数建议（例如 800–1500 字）。
  2. 当处于 current 状态的故事弧超过 N 条时，自动发起相邻弧的合并。

**M9. 任务面板只显示 active 状态的任务**
- 位置：`story_repository.py:808-811`、`GameWorkspace.tsx:125`。
- 影响：模型创建的 offered/eligible 任务（也就是“机会已出现”的任务）玩家看不到，再加上 B1，玩家更难意识到可以接任务。
- 建议修法：投影同时返回 offered 状态的任务（以及最近的终局任务），前端分组显示。

### 低

- **L1. EXP 无法扣减，也没有单次数值参考**：`gm_turn.schema.json:185` 的 `amount ≥ 0`，而文档 `经验值功能设定.md:36` 写“经验增减”。单条最多 100000、每回合最多 20 条，只有封顶阈值兜底。建议在契约中给出各阶单次参考区间（例如占阈值的 3–15%），并删掉文档里的“减”字。
- **L2. 零变化的提案也要求逐字证据**：运行时策略写“非零”（`content_registry.py:493`），而 `narrative_contract.py:711-714` 对所有非空 evidence 都做检查。建议让两处一致，例如对 `delta==0` 的条目跳过检查。
- **L3. 对已有物品 add 时静默忽略其他字段**：`narrative_contract.py:977-982` 只叠加数量，`equipped`、`power`、`description` 都被丢弃；而 `item_id=null` 的同名物品会生成重复条目。建议在契约中写明“可堆叠物品复用 item_id”，并在 add 时校验不一致的字段。
- **L4. 新建任务允许 `name=null`**：`narrative_contract.py:498-500, 1044`。会在面板上显示成空标题。建议 create 时强制要求 name 和 description。
- **L5. supersede 只删除旧记忆**：`story_repository.py:749-752`，`superseded_by` 字段从未写入。建议在契约中写明“替代时需同时 create 一条新记忆”，或由程序自动关联。
- **L6. JSON 后面带普通文字会被误判为多个 JSON 值**：`model_provider.py:292-322`。实测 `{...}\n（共3项变更）` 与 `{...}\n以上为 "turn" 结果` 都会报错。有重试兜底，开启 json_schema 时也很少出现。建议只在剩余文本以 `{` 或 `[` 开头时才视为第二个 JSON 值。
- **L7. 7 个声望键缺少语义说明**：只给了枚举 ID。建议说明 continental_overall 只用于跨势力、广泛传播的事件，地方行为按所在 `jurisdiction_id` 选择对应势力键。
- **L8. schema 范围与 validator 范围不一致**：属性 ±35 对 ±100（`:421`），羁绊 ±50 对 ±35，声望 ±100 对 ±50。建议统一，以免报错文案误导排查。
- **L9. 天赋改动不会同步回 `identity.talent`**：提示词里会同时出现旧的天赋原文和新的天赋列表。

## 四、修复方案确认（2026-10-18）

以下方案已与产品负责人逐项确认，作为落地依据。未单独列出的问题（M3、M4、L2–L8）按第二节的“建议修法”执行。

### 需要决定的规则

| 编号 | 确认的方案 |
|---|---|
| B1 接任务、开始突破的意图判定 | 去掉程序里的关键词表，改由模型判断玩家意图。模型须引用玩家原话中表达该意图的那一小段；程序只校验两点：这段话确实出自本次玩家输入，且所在分句不含否定（如“不接”“先不突破”）。提示词写明引用方式。 |
| H1 羁绊、声望单次上限 | 沿用现有数值。羁绊：轻微 5、中等 15、重大 25、改变一生 35；声望：轻微 5、中等 15、重大 35、影响世界 50。均可正可负。把两张表写进提示词，并把输出格式里的范围统一为羁绊 ±35、声望 ±50，报错信息带上该档上限。 |
| H2 故事弧自动总结的重试 | 不设次数上限：每次新剧情保存后，同一批节点都会再试一次。同一批累计失败超过 3 次后，用游戏提示告诉玩家“故事弧多次整理失败”及失败原因。记忆管理页增加“重新整理故事弧”按钮，玩家随时可以手动发起。 |
| H3 短期资源上限 | 每升一阶，程序把 HP/MP/SP/ST 四项上限按 ×1.3 提高，当前值同时补上上限的增量。体质等其他因素暂不影响上限。 |
| H4 满 EXP 时的突破任务 | 6 阶及以上 EXP 刚满时，由程序自动创建一个“可触发”的突破任务，交给模型在后续剧情中展开，不再整回合拒绝。玩家拒绝或任务失败后不再自动重建，之后由玩家主动发起突破。 |
| H5 角色死亡 | 死亡即结局。死后不能再提交“自由行动”或“干涉命运”，只能用“重塑命运”改写最近一段（回到死亡之前），或去玩其他存档。剧情页显示结局状态和重塑入口。 |
| M1 天赋与技能 | 新增提示词说明：天赋是先天或极少变化的特质，只在重大事件中获得；技能通过学习、训练获得或提升。初始天赋在剧情有充分依据（如诅咒、重伤）时允许修改或移除。add 时 id 填 null，update/remove 必须使用权威状态中已有的 id，程序也会校验。 |
| M2 年龄 | 新增年龄变化提案，模型可根据剧情中流逝的时间修改年龄，也允许返老还童等特殊事件让年龄减少。与其他数值一样需要引用正文作为依据，程序只保证年龄不低于 1。提示词写明正常情况下年龄只随时间增长。年龄变化显示在剧情页“本段带来的变化”中。 |
| M5 长期属性单回合幅度 | 程序上限为 ±20，且提示词写明只有重大正向或负向事件才能达到这个幅度。常规增减建议 1–3，这个建议只写在提示词里，程序不校验。 |
| M6 装备 40% 上限 | 超出部分不计入有效战力，并在 GM 提示中说明，不再整回合拒绝。权威状态中提供上限与剩余余量供模型参考。 |
| M7 战力修正 | 按严重程度设上限：minor/moderate/major/extreme 分别不超过基础战力的 10%/25%/50%/100%。提示词写明伤势痊愈、离开对应环境、强化结束时必须移除对应的临时修正。不做自动过期。 |
| M8 故事弧压缩 | 正在使用的故事弧达到 4 条时，自动把最早的 3 条合并为 1 条，最新一条保持不动；手动合并仍可用。提示词写明只总结 `current_action.frozen_sources`，梗概建议约 800–1500 字。 |
| M9 任务栏 | 分三组显示：进行中、待接取（已提供给玩家）、已结束（完成/失败/拒绝/放弃，可折叠）。尚未触发的任务仍然隐藏。 |
| L1 EXP | 只增不减。设定文档中的“经验增减”改为“经验增加”，提示词给出单次 EXP 的参考量。 |
| L9 天赋原文 | `identity.talent` 保留为建卡时的原始记录（角色详细信息中显示的就是它），不随游戏变化。提示词写明当前天赋以 talents 列表为准。 |

### 老存档

`output_contract.txt` 和 schema 会冻结进每个存档的内容修订，改动只对新存档生效。所以以上规则凡是涉及模型行为的，都同时写进 `content_registry.py` 的运行时策略，让老存档也生效。程序侧的校验需要同时兼容新旧两版契约字段。
