# Fantasy Simulator 第一阶段实现规划

> 文档状态：规划稿 v1.0  
> 编写日期：2026-09-27  
> 本阶段交付边界：前后端可运行雏形、多存档、模型设置、完整角色创建与确认入档；不实现正式游戏回合。

## 1. 规划依据与优先级

本规划按以下优先级解释现有资料：

1. `功能需求文档.md` 是第一阶段产品范围的唯一基准。
2. `AI长篇叙事应用工程实践参考.md` 提供架构与工程经验，按当前阶段取舍，不照搬完整长篇叙事系统。
3. 世界观、种族、势力、地理、奇观、属性、战力和经验等设定文档是角色创建选项与校验规则的事实来源。
4. `GM模型核心行为规则.md` 和 `地区引导主线.md` 主要服务第二阶段；第一阶段只预留版本化规则入口，不实现 GM 游戏循环。

如果不同文档出现冲突，先遵循需求文档确定功能范围，再遵循世界基础设定确定世界事实；无法据此消解的内容列为产品决策，不由代码擅自补设。

## 2. 阶段目标与完成定义

第一阶段完成后，玩家应能在浏览器中完成以下闭环：

1. 启动 Python 后端并进入网页前端。
2. 创建、切换、重命名、删除、导入和导出多个独立存档。
3. 配置模型服务并测试连通性，设置叙事偏好和模型思考开关。
4. 在任意存档中完成 13 步角色创建；中途退出或切换存档后可以继续。
5. 请求模型生成初始属性与战力候选，并在生成期间切换到其他存档继续操作。
6. 查看完整角色面板，通过补充意见重新生成，或接受当前候选。
7. 接受后将角色原子写入正式存档，并进入只展示角色与开局地点的游戏壳页面。

第一阶段的“游戏开始”定义为：存档状态从角色创建切换为 `ready`，正式角色和起始世界信息已经持久化，第二阶段可以在此基础上开启首个 GM 回合。游戏壳不伪装成已经具备自由行动能力。

## 3. 范围边界

### 3.1 本阶段包含

- 网页应用壳、路由、基础布局、错误提示与加载状态。
- Python API 服务、数据库迁移、统一错误格式和基础日志。
- 版本化世界资料目录，包括八个可玩种族、兽裔分支、11 个初始地点、势力目录、阶位称号和叙事设置项。
- 多存档生命周期与跨存档隔离。
- JSON 存档导入与导出。
- 模型配置、密钥隔离、连通性与能力检测。
- 13 步角色创建、草稿自动保存、前后端双层校验。
- 异步角色生成、结构化输出解析、候选校验、重新生成与确认。
- 已确认角色面板和游戏壳页面。
- 针对关键规则、API、并发隔离、导入导出和主流程的自动化测试。

### 3.2 本阶段不包含

- 玩家行动输入、正式 GM 叙事、回合提交与选项生成。
- 战斗推演、伤害、资源消耗、状态效果和装备系统。
- EXP 结算、升级、突破与成长系统。
- NPC 关系、任务、地区引导主线、动态世界事件。
- 长期记忆、故事弧、历史浏览、重塑当前幕。
- 多用户账户、云同步、联机玩法和权限系统。
- Windows 安装包、便携版或移动端打包。
- 设定图生成；第一阶段只提供稳定的图片占位和资源路径。

## 4. 关键产品解释与待确认项

### 4.1 本规划采用的默认解释

- 应用以本地单玩家使用为第一目标，但浏览器与后端之间仍按不可信网络边界设计。
- “八个可玩种族”建模为人类、羽族、海族、兽裔、精灵、龙族、矮人、魔族；选择兽裔后必须再选“兽人”或“半兽人”分支。
- 界面展示所有种族的 1–10 阶体系，因为这是需求中的明确展示项；最终是否允许选择会改变“当前无十阶强者”等世界现状的组合，由种族 × 阶位矩阵决定。矩阵确认前不默认放行，也不擅自禁用；六阶以上始终显示游戏性警告。
- 平均寿命仅作信息提示，不等同于年龄上限。没有设定依据时，不用自创成年年龄或种族年龄硬校验。
- 长期属性 CON、INT、CHA 必须处于 1–100；HP、MP、SP、ST 的绝对标尺和当前值口径待规则确认，不能先假定一律满值。
- 基础战力由所选阶位和设定表确定，EXP 固定为 0。有效战力在修正规则确认前默认等于基础战力，不接受模型提供无规则依据的裸修正值。
- 势力步骤是纯浏览步骤，不产生角色字段，也不提供加入或“不加入”选择。页面展示每个势力的介绍及玩家在其中可获得的任务、服务、活动等机会，并提示“本步骤无需选择；符合条件的势力可在游戏过程中加入”。加入条件和流程留待游戏阶段设计。
- API 配置和模型思考偏好是应用级本地配置；思考偏好不进入存档和导出。三项叙事偏好保存为应用默认值，并在创建存档时复制一份到存档中，方便未来按存档覆盖和随存档导出。
- 导入存档永远分配新的本地存档 ID，保留来源 ID 作为追踪信息，不静默覆盖已有存档。

### 4.2 开发前需要确认的 P0 产品规则与资料

这些问题不阻碍 M0 工程骨架，但会阻断对应的角色规则、资料配置和 M3/M4 功能验收：

1. **势力展示资料**：为 12 个核心势力整理玩家可获得的任务、服务、活动与其他互动机会，并标注公开对象、前置条件和设定来源；本阶段不定义或校验加入资格。
2. **种族与等阶限制**：精灵出生至少具备三阶基础魔力，海族陆地形态、成年羽族和成年龙族也有典型阶位描述；这些是提示还是角色创建硬门槛，需要明确。
3. **短期资源数值口径**：定义 HP、MP、SP、ST 最大值的合法范围、是否可跨角色比较、当前值由模型生成还是默认满值，以及是否允许耗尽或负伤开局。
4. **初始有效战力**：是否一律等于基础战力，还是允许模型依据天赋与身世给出可解释修正；如允许，需要定义创建阶段可用的修正上限和原因类别。
5. **特殊起点保障**：为深海沧渊城、高温熔脊龙谷、精灵核心区等组合定义准确落脚点、访问许可与必要生存保障。可由起点默认提供叙事性保障，不必因此提前实现装备系统，但必须有策划规则依据。
6. **初始装备、技能和货币**：当前角色创建未要求这些字段，本规划不生成；若完整角色面板必须展示，应先补充规则后再扩展生成契约。
7. **预设词内容**：外貌、性格、天赋预设词是硬需求，但现有设定未提供清单；M0 需给出稳定 ID、显示文案、适用种族和追加/去重规则并完成策划确认。
8. **存档管理细节**：删除是否需要回收站、导出是否包含尚未接受的角色候选。本规划默认删除二次确认且不可恢复，导出包含草稿和当前候选但不包含运行中任务。
9. **技术限制表**：实施前确定姓名和各自由文本长度、导入文件与模型响应体积、URL 长度、超时范围、结构化字段数量等限制；前后端、模型 Schema 和测试引用同一份版本化常量。

P0 项应形成一份机器可读的规则配置和一份人工验收清单。确认前可以搭建结构，但不应把临时猜测固化为世界规则。

## 5. 推荐技术方案

### 5.1 总体形态

采用单体仓库、前后端分离开发、单进程本地部署的起步形态：

```text
Browser
  -> React + TypeScript 单页应用
  -> /api HTTP/JSON
  -> FastAPI 应用
       -> 应用服务与规则裁决
       -> SQLite（权威状态）
       -> 世界资料静态目录
       -> LLM Provider Adapter
```

选择这一形态的原因是第一阶段领域边界清晰、部署目标偏本地，不需要微服务或外部消息队列；同时前后端 API 边界可为未来桌面壳、远程部署和测试替身保留空间。

### 5.2 前端建议

- React + TypeScript + Vite：负责 SPA、组件和构建。
- React Router：存档、设置、创建向导、角色确认和游戏壳路由。
- TanStack Query：后端权威状态、请求缓存、轮询生成任务和按存档 ID 隔离缓存键。
- React Hook Form：分步表单、字段状态和局部校验。
- 前端运行时 Schema 校验库：校验 API 响应和导入预览，不把 TypeScript 类型误当运行时保障。
- CSS 变量与模块化样式：先建立颜色、间距、排版和状态 token，不在第一阶段引入沉重设计系统。

具体依赖版本在实施首个提交时锁定，避免规划文档中的版本号提前过期。

### 5.3 后端建议

- FastAPI：提供类型明确的 HTTP API 和自动接口文档。
- Pydantic：请求、响应、LLM 结构化输出和导入文件校验。
- SQLAlchemy + Alembic：持久化与可演进数据库迁移。
- SQLite WAL：满足本地单玩家多存档并发读写；所有写入保持短事务。
- httpx：模型服务调用、超时和取消传播。
- pytest：规则、仓储、API、模型适配器和并发测试。

第一阶段使用数据库驱动、进程内执行的异步任务，不引入 Redis/Celery。任务先持久化为 `queued`，执行器通过条件更新原子领取为 `running`；启动时重新调度未领取任务，并将无有效租约的陈旧任务标记为 `interrupted`。重试创建关联原任务的新 attempt。每个模型配置提供 `max_concurrency`，默认 1；“可切换存档继续操作”不要求上游模型必须并行推理。第一阶段部署固定为单 API 进程，未来更换执行器不改变领域 API。

### 5.4 建议目录边界

```text
Fantasy Simulator/
  apps/
    web/                       # 前端应用
    api/                       # Python 后端
      app/
        api/                   # HTTP 路由与 DTO
        application/           # 用例编排
        domain/                # 存档、角色、规则与状态机
        infrastructure/        # DB、密钥、LLM、日志实现
        world_data/            # 版本化机器可读设定
      migrations/
      tests/
  docs/
  tests/
    e2e/                       # 跨前后端主流程
```

世界资料与业务规则应进入版本控制中的结构化数据文件，不在运行时解析 Markdown。原始 Markdown 保留为策划资料和事实依据，结构化目录通过人工校对与测试保证一致性。

## 6. 核心领域模型

### 6.1 存档状态机

存档主状态只有 `draft/review/ready`，生成任务独立记录 `queued/running/succeeded/failed/cancel_requested/cancelled/stale/interrupted`。首次生成期间存档仍为 `draft`，合法候选原子写入后转为 `review`；重新生成期间保持 `review` 并继续展示旧候选，同时标记“新版本生成中”；失败或取消只改变任务状态。只有确认最新合法候选才能转为 `ready`。生成任务不是存档排他锁，玩家仍可读取当前存档或操作其他存档。

### 6.2 主要实体

| 实体 | 关键字段 | 说明 |
|---|---|---|
| Save | `id`、`name`、`phase`、`revision`、`ruleset_version`、时间戳 | `id` 使用 UUID；`revision` 用于乐观并发控制。 |
| SavePreferences | 三项叙事设置 | 属于存档，可随导出迁移。 |
| CharacterDraft | 13 步原始输入、当前步骤、`draft_revision` | 自动保存；自由输入保留原文。 |
| GenerationJob | `id`、`save_id`、请求 ID、草稿版本、attempt、状态、租约、错误码、时间戳 | 隔离异步工作并支持原子领取、轮询、取消和恢复。 |
| CharacterCandidate | 关联任务、结构化模型提案、程序裁决结果、警告、生成元数据 | 可替换但不直接成为正式角色。 |
| Character | 身份、起点、属性、战力、EXP、规则版本 | 玩家确认后创建的权威角色。 |
| ModelProfile | 服务地址、模型名、能力、非敏感参数 | 不包含 API Key 明文。 |
| SecretReference | 密钥引用 | 由密钥存储实现管理，永不进入存档 JSON。 |

### 6.3 正式角色字段边界

- 身份：姓名、性别文本、年龄、种族、可选种族分支。
- 描述：外貌、性格、天赋、身世、其他补充。
- 起点：初始地点与当前地点；第一阶段角色没有初始势力字段。
- 成长：战斗阶位、展示称号、EXP=0、下一阶所需 EXP；十阶标记为当前体系最高阶。
- 长期属性：CON、INT、CHA，范围 1–100，并附生成理由。
- 短期资源：HP、MP、SP、ST 的当前值与最大值；具体标尺和开局当前值按 P0 规则配置。
- 战力：基础战力、有效战力、修正项和解释。
- 溯源：规则集版本、LLM 输出契约版本、提示词版本、候选 ID 和确认时间。

首阶段不把职业、技能、装备、货币和关系以空壳实体塞入正式角色。存档导出保留顶层 `extensions`，第二阶段通过迁移增加真实模型。

## 7. 世界资料建模

### 7.1 资料目录内容

第一批结构化世界资料至少包括：

- 八个种族及兽裔分支：稳定 ID、名称、短介绍、平均寿命文案、特征、阶位称号、创建提示、图片占位路径。
- 1–10 阶基础战力表：100、180、320、560、1000、1800、4000、9000、20000、100000。
- 经验阈值表：未入阶到一阶为 80，之后依次为 100、140、200、300、450、650、900、1300、2000；十阶显示已达当前体系最高阶。
- 11 个初始地点：稳定 ID、名称、归属区域、短介绍、环境提示、准确落脚点、必要生存/访问保障、图片占位路径。
- 12 个核心势力：稳定 ID、名称、介绍、任务/服务/活动等互动机会、公开对象或前置条件说明、设定来源、图片占位路径；不包含初始加入选项。
- 种族 × 阶位矩阵：区分硬禁用、稀有性警告和会改变当前世界现状的特殊组合。
- 外貌、性格、天赋预设词：稳定 ID、显示文案、适用种族和追加/去重规则。
- 叙事设置：步进速度 `slow/fast/dynamic`，倾向 `casual/balanced/combat`，详细度 `concise/standard/detailed`。
- 推荐叙事默认值：动态、平衡、标准。

兽人和矮人没有正式的种族专属战斗称号。界面应显示“一阶”至“十阶”及“无专属称号”，不能把矮人工匠等级当作战斗阶位，也不能临时创造称号。

### 7.2 资料版本与校验

- 每份目录数据使用稳定机器 ID，显示名称可以独立演进。
- 规则集具有显式版本，如 `world-rules/1`；存档记录创建时使用的版本。
- 启动测试检查 ID 唯一、十阶数据完整、地点数量和种族数量符合需求、限制引用有效。
- 图片字段从第一天存在，但缺图时统一展示占位图与替代文本。
- 角色草稿保存稳定 ID，不保存依赖 UI 文案的数组序号。

## 8. 角色创建体验

### 8.1 页面结构

角色创建使用桌面端优先、可响应式收缩的双栏向导：左侧显示 13 步进度和已填摘要，右侧显示当前表单。种族和地区步骤使用可选择的资料卡；势力步骤使用“势力导航 + 设定图占位 + 介绍 + 可获得内容”的只读资料卡。

13 步保持与需求一致：

1. 种族：八个一级种族；兽裔选择后出现必选分支。
2. 姓名：必填文本。
3. 性别：男、女预设和自定义文本三选一，自定义时填写内容。
4. 年龄：显示种族或分支寿命文案，输入正整数。
5. 外貌：预设标签点击后写入可编辑文本，允许组合与自由补充。
6. 性格：同外貌交互。
7. 等阶：展示 1–10 阶和对应称号；按种族 × 阶位矩阵禁用明确不允许的组合，其他六阶以上选择显示非阻断游戏性警告。
8. 天赋：预设标签与自由文本组合。
9. 身世：可空长文本。
10. 地区：在 11 个地点间浏览并选择。
11. 势力：切换浏览全部势力及可获得的任务、服务和活动，不提供选择控件；显示“本步骤无需选择；符合条件的势力可在游戏过程中加入”，玩家可直接进入下一步。
12. 其他补充：可空长文本。
13. 模型生成：确认输入摘要、发起生成、查看候选、重新生成或接受。

### 8.2 草稿与校验策略

- 每步“下一步”前做即时前端校验；后端保存时重复完整校验。
- 草稿按存档独立自动保存，文本输入采用短暂防抖。应用内切档或跳转时等待最后一次保存成功；保存失败或仍有未提交修改时阻止离开并允许重试。浏览器强制关闭无法承诺完成普通异步请求，界面需用“已保存/保存中/保存失败”状态如实提示。
- 修改种族后，重新校验兽裔分支、年龄提示和阶位称号；势力步骤不保存选择，因此不触发势力资格校验。
- 自由输入设合理的技术长度限制、字符计数和清晰错误，不做题材内容审查或擅自改写。
- 每次保存携带 `expected_revision`。版本冲突时展示服务器最新草稿，不用后到请求静默覆盖先到请求。
- 已确认角色默认不可回到创建向导修改；重开角色应作为新存档，避免第一阶段引入复杂回滚语义。

## 9. 模型配置与调用边界

### 9.1 模型配置

第一阶段以 OpenAI-compatible HTTP 协议作为首个适配器，配置项包括：

- API Base URL
- API Key
- 模型标识
- 请求超时（默认 300 秒，可在 1–600 秒内配置）
- 是否请求结构化输出
- 模型思考偏好
- 最大调用并发数（默认 1）

业务层只依赖统一 `ModelProvider` 接口，供应商特有参数由适配器转换。设置页的“测试连接”应验证鉴权和目标模型可用性，并返回能力结果；测试成功不写入游戏存档。

“模型思考”不是所有服务都支持。适配器返回 `controlled/unsupported/unknown`，并附带策略、`verified/accepted_bundle/unsupported/unknown` 置信度和说明。未知与不支持时开关保持开启并禁用，表示模型采用服务默认行为或不受应用控制；只有 `controlled` 才允许保存开关。不能按模型名称硬编码，也不能把供应商参数散落到角色创建代码中。

连接测试优先使用模型列表等无生成接口验证鉴权与模型存在性；基础连接成功后发送一个最小聊天请求，同时携带七种兼容参数：`enable_thinking=false`、`thinking.type=disabled`、`reasoning_effort=none`、`chat_template_kwargs.enable_thinking=false`、`reasoning.enabled=false`、`reasoning.effort=none`、`thinking_config.thinking_budget=0`。组合中的两项嵌套 reasoning 参数合并为 `reasoning: {enabled:false, effort:"none"}`，避免同名顶层对象互相覆盖。HTTP 成功即记为 `accepted_bundle`；仅在 400/422 明确拒绝参数时按上述顺序逐项探测，首个成功记为 `verified`，全部明确拒绝记为 `unsupported`。字段归因同时识别顶层字段和 `reasoning.enabled`、`reasoning.effort`、`thinking_config.thinking_budget` 等嵌套路径；两个 reasoning 策略仍各自单项探测。鉴权、429、5xx、超时和网络错误立即按真实错误中止，不误判参数能力；不因输出格式不符误判。能力结果按 Base URL、模型标识和 v2 配置版本缓存，缓存不含密钥，成功探测会覆盖为七策略结果。运行时按缓存策略发送开关对应值；新增策略开启值分别为 `reasoning.enabled=true`、`reasoning.effort=medium`、`thinking_config.thinking_budget=-1`（自动思考）。缓存策略被明确拒绝后，会按七种策略顺序用真实生成请求寻找替代并缓存首个成功策略；全部拒绝后仅做一次无控制参数回退，保持重试有界和权威状态只提交一次。M2 测试覆盖以上分支。

### 9.2 密钥安全

- API Key 与 SQLite 游戏状态、导出 JSON、日志和前端持久化完全分离。
- 后端接收密钥后写入 `CredentialStore`，优先使用操作系统凭据存储；无可用安全存储时允许仅会话保存或环境变量注入，并向玩家说明不会持久化。
- 设置读取接口只返回是否已配置和掩码，不返回完整密钥。
- 日志、异常、模型请求诊断和测试快照统一脱敏。
- Base URL 只允许 HTTP/HTTPS；若未来远程部署，应额外限制内网地址访问以防 SSRF。本地模式也要显示自定义地址将由后端访问的提示。

### 9.3 角色生成输入

发送给模型的上下文只包含本次生成所需资料：

- 固定角色生成规则与输出契约。
- 玩家 12 步输入和重新生成意见。
- 当前种族和地点的精简资料卡；势力步骤没有玩家选择，不作为角色生成输入。
- 属性语义、所选等阶和基础战力。
- 不可违背的世界基础规则摘要。

不把全部 Markdown、无关人物志、所有地区主线和整份工程参考塞入上下文。玩家输入放入明确的数据区，并在系统规则中声明其不能覆盖规则和输出契约。

### 9.4 结构化候选输出

模型输出必须使用版本化结构，至少包含：

- CON、INT、CHA 数值与逐项理由。
- HP、MP、SP、ST 最大值、当前值与逐项理由；仅在 P0 标尺确认后启用。
- 有效战力提案、相对基础战力的修正项与理由；仅在 P0 修正规则确认后启用，否则程序固定为基础战力。
- 角色整体能力概述、优势、局限和设定一致性提示。
- 与玩家输入存在冲突时的警告，不替玩家重写姓名、性别、种族、地区等已确定字段。

程序收到结果后只裁决可确定验证的规则：Schema 与稳定 ID、种族/起点资格、属性和已批准的资源边界、基础战力与有效战力修正规则、EXP 初值与阈值、候选归属和版本。其他自然语言世界观一致性通过提示词约束并以警告展示，不宣称程序能完整证明。硬规则字段以程序结果为准；模型原始提案与实际采纳结果分开保存，便于诊断。

解析失败可以携带原响应发起一次仅修复格式的受限模型请求；不在本地猜测性拼补 JSON。再次失败则任务失败并提供可重试错误。业务冲突不能靠“修 JSON”掩盖，应返回明确校验警告或拒绝原因。

## 10. 并发、多存档与防串档设计

每个修改性请求必须同时包含：

- 路径中的 `save_id`
- 客户端生成的 `request_id`
- `expected_revision` 或 `draft_revision`

角色生成流程如下：

```text
校验 save_id 和草稿版本
  -> 创建 GenerationJob 并提交短事务
  -> 在事务外调用模型
  -> 解析并裁决候选
  -> 重新读取 save_id、save revision、草稿版本和任务状态
  -> 存档仍为 draft/review、尚无正式角色且各版本一致：原子写入候选并完成任务
  -> 版本已变化：任务标记 stale，不覆盖当前候选
```

关键约束：

- 前端查询缓存键始终包含存档 ID，不能用一个全局 `currentCharacter` 接住任意响应。
- 切换存档只改变当前视图，不自动取消其他存档的后端生成。
- 每个任务响应携带 `save_id` 和 `job_id`；前端只更新匹配的存档状态。
- 同一存档只允许一个活跃角色生成任务，通过活动槽位表或等效的数据库唯一约束与原子创建保证，不能依赖“先查后写”。玩家重新生成时可取消旧任务，取消失败也必须靠版本检查阻止旧响应覆盖。
- 模型调用期间不持有数据库事务或全局锁。
- `request_id` 建唯一约束，网络重试返回同一个任务，不重复扣费或生成。
- SQLite 开启 WAL 和合理 busy timeout；数据库写锁只覆盖校验后的短原子提交。

确认角色请求必须携带 `candidate_id`、`expected_save_revision`、`expected_draft_revision` 和幂等请求 ID。在单个事务中复核：候选属于目标存档、来源任务成功、候选未被替代、草稿版本仍一致、存档尚无正式角色；随后把该存档所有活动生成任务标为 `cancel_requested` 或 `stale`，以唯一约束创建 Character、将存档切换为 `ready` 并递增 revision。并发确认只能有一个成功。取消请求先进入 `cancel_requested`；即使上游调用无法真正中断，迟到结果也必须复核任务仍为 `running`、存档仍为 `draft/review`、尚无正式角色、save/draft revision 均一致，否则丢弃。

## 11. API 规划

接口路径是建议契约，实施时可微调命名，但不应改变资源边界。

### 11.1 世界资料与设置

- `GET /api/world/catalog`：返回种族、地点、势力、阶位和规则集版本。
- `GET /api/settings`：返回非敏感配置、密钥配置状态和叙事默认值。
- `PUT /api/settings/model`：更新模型配置与可选密钥。
- `POST /api/settings/model/test`：测试连接并返回能力检测。
- `PUT /api/settings/narration`：更新应用默认叙事设置。

### 11.2 存档

- `GET /api/saves`：列表和各存档阶段/生成摘要。
- `POST /api/saves`：创建空白存档并复制默认叙事设置。
- `GET /api/saves/{save_id}`：读取存档摘要。
- `PATCH /api/saves/{save_id}`：重命名等元数据修改。
- `DELETE /api/saves/{save_id}`：二次确认后删除；先阻止新任务并取消活跃任务，再级联清理从属数据，迟到响应无条件丢弃。
- `GET /api/saves/{save_id}/export`：在一致性只读事务中生成版本化 JSON 文件并记录对应 revision。
- `POST /api/saves/import/validate`：只校验并返回导入预览。
- `POST /api/saves/import`：原子导入并分配新 ID。

### 11.3 角色创建

- `GET /api/saves/{save_id}/character-draft`
- `PUT /api/saves/{save_id}/character-draft`
- `POST /api/saves/{save_id}/character-generations`
- `GET /api/saves/{save_id}/character-generations/{job_id}`
- `POST /api/saves/{save_id}/character-generations/{job_id}/cancel`
- `GET /api/saves/{save_id}/character-candidate`
- `POST /api/saves/{save_id}/character/confirm`
- `GET /api/saves/{save_id}/game-bootstrap`

所有错误统一返回稳定错误码、用户可读信息、字段错误、可否重试和追踪 ID。至少区分：输入无效、存档不存在、版本冲突、种族或起点资格不符、模型未配置、模型鉴权失败、超时、输出格式错误、生成结果过期和导入格式不兼容。

## 12. 存档导入导出契约

导出 JSON 顶层建议包含：

- 格式标识与 `schema_version`
- 导出时间、应用版本、规则集版本
- 存档元数据和来源存档 ID
- 存档叙事偏好
- 角色创建草稿
- 当前非敏感候选及裁决结果
- 已确认角色与游戏阶段
- 为后续迁移保留的 `extensions`

明确排除：API Key、鉴权头、密钥引用内部值、本机绝对路径、日志、追踪信息、运行中任务、缓存和数据库内部主键关系。

导出在一致性只读事务中读取 Save、Draft、Candidate 和 Character，并记录 `save_revision` 与 `draft_revision`，避免与自动保存或候选完成交错成混合快照。导入采用两阶段流程：先上传并完整校验，在预览中展示版本、角色、来源和警告；玩家确认后，以单事务写入新存档。未知主版本拒绝导入，旧的兼容版本通过显式迁移转换。任何字段失败都不能留下半个存档。

## 13. 前端页面与导航

### 13.1 应用壳

- 左侧存档列表：名称、阶段、角色名、生成状态和切换入口。
- 主区域：当前存档对应页面。
- 顶栏：新建、导入、导出、设置和后端连接状态。
- 小屏幕下存档列表折叠为抽屉，不牺牲生成状态可见性。

### 13.2 主要路由

- `/`：存档列表与欢迎页。
- `/settings`：模型与叙事默认设置。
- `/saves/:saveId/create/:step`：角色创建向导。
- `/saves/:saveId/review`：完整角色候选与重新生成。
- `/saves/:saveId/game`：正式角色、起始地点和“第一阶段完成”的游戏壳。

加载、空状态、连接失败、模型失败、过期响应和版本冲突都要有专门界面反馈，不能只在控制台报错。

## 14. 实施顺序

建议用六个可独立验收的纵向里程碑推进。

### M0：规则确认与工程基线

- 确认第 4.2 节全部 P0 规则与资料，特别是势力互动机会、种族 × 阶位、初始数值、特殊起点保障和三类预设词。
- 将角色创建所需世界资料整理为版本化数据并进行策划校对。
- 建立前后端工程、格式化、静态检查、测试和本地启动方式。

验收：前后端健康检查可用；世界资料完整性测试通过；无业务功能伪实现。

### M1：应用壳与多存档

- 数据库迁移、存档仓储和存档 CRUD。
- 前端应用壳、存档列表、创建/切换/重命名/删除。
- revision、统一错误和基础日志。

验收：两个存档的修改互不影响；刷新后状态仍在；错误存档 ID 不会退化为当前存档。

### M2：设置与模型连通性

- 模型适配器、凭据存储抽象、设置 API 和设置页。
- 连接测试、超时、鉴权错误、能力检测和密钥脱敏。
- 三项叙事设置及推荐默认值。

验收：可配置真实或测试模型端点；连接测试清楚提示可能费用，能区分鉴权、限流、超时、服务端错误和参数不支持；能力缓存按配置失效；密钥不出现在读取接口、日志、数据库游戏表和导出中。

### M3：角色创建 1–12 步

- 世界资料 API 和种族/地点/势力浏览卡。
- 完整分步表单、预设词、自定义文本、势力只读浏览、起点提示和高阶警告。
- 后端校验、草稿自动保存与恢复。

验收：13 步前的所有字段可正确填写；切存档、刷新和返回上一步不会串数据或丢失已保存草稿。

### M4：模型生成、重生成与确认

- GenerationJob、异步执行器、结构化输出契约和程序裁决。
- 生成状态轮询、错误/取消/重试、候选面板和修改意见。
- 确认角色的原子事务与游戏壳。

验收：角色完整闭环可用；生成期间可操作另一存档；旧响应、重复请求和草稿版本变化均不能覆盖当前候选。

### M5：导入导出与发布前加固

- 版本化 JSON 导出、导入预检、迁移和冲突处理。
- 主流程 E2E、异常路径、无障碍基础检查和响应式检查。
- 文档补全：启动、配置、数据位置、备份、已知限制。

验收：存档可往返导出导入且语义一致；非法或不兼容文件不会部分写入；全套质量门禁通过。

## 15. 测试策略

### 15.1 后端单元与集成测试

- 种族分支、阶位称号、基础战力、长期属性范围和起点资格。
- 存档状态机、任务原子领取/重启恢复、revision 冲突、请求幂等和并发确认事务。
- LLM 合法输出、非法 JSON、缺字段、越界值、超时、取消和一次修复重试。
- 两个存档独立排队或并行生成、同存档重复提交、草稿变更导致旧结果 stale。
- 导出一致性快照与敏感字段排除、导入 Schema、版本迁移、ID 冲突和事务回滚。
- 活跃生成中删除存档、取消后迟到响应、输入后立即切档等竞态测试。
- 重新生成与确认旧候选并发时，确认事务会使活动任务失效，迟到新候选不能写入 ready 存档。

模型测试使用可编程假实现，不依赖外网或产生调用费用；少量真实服务冒烟测试单独运行。

### 15.2 前端组件与流程测试

- 13 步导航、必填/可空字段、预设词写入、兽裔分支和自定义性别。
- 种族变化后的寿命、称号和相关创建规则更新。
- 高阶警告、势力机会展示与无需选择提示、缺图占位和键盘操作。
- 查询缓存按 save ID 隔离，切档后迟到响应不污染当前视图。
- 生成中、失败、过期、取消、重试、确认和游戏壳状态。

### 15.3 端到端关键场景

1. 新建存档 A，填写部分角色，刷新并恢复。
2. A 发起生成后切到存档 B，完成 B 的编辑；A 完成时 B 页面不被覆盖。
3. A 生成期间修改草稿，旧结果被标记过期且不能确认。
4. 同一生成请求因网络重试提交两次，只产生一个任务。
5. 合法角色候选确认后进入游戏壳，EXP 为 0、经验条阈值和基础战力正确。
6. 导出 A、删除原存档、重新导入，新 ID 下角色与偏好保持一致。
7. 导入含密钥字段、坏版本或截断 JSON 的文件，系统拒绝且数据库无残留。
8. 同时确认同一个候选两次，数据库中只产生一个正式角色。
9. 生成中删除存档或请求取消，迟到模型响应不能复活或污染已删除/当前状态。

## 16. 非功能要求与质量门禁

- **正确性**：后端是权威状态源；模型输出和前端状态均不能绕过规则校验。
- **隔离性**：所有存档读写和生成结果均可追溯至明确存档 ID。
- **可靠性**：写操作短事务，导入与角色确认原子完成，异常重启后任务状态可解释。
- **安全性**：密钥隔离与脱敏，导入大小限制，上传内容不执行，自定义 Base URL 有风险提示。
- **可观测性**：日志包含追踪 ID、存档 ID、任务 ID、耗时和归一化错误，不记录密钥或完整敏感提示词。
- **可维护性**：世界资料、领域规则、模型适配和 HTTP 路由分层；设定不散落在 UI 条件判断中。
- **体验**：所有耗时操作有状态与取消入口；错误能解释下一步；主要流程支持键盘操作和清晰焦点。
- **资源边界**：版本化技术限制表统一约束输入长度、导入/响应体积、超时和结构化字段，避免前后端与模型契约不一致。

合入门禁建议包括：后端格式化/静态检查/测试，前端格式化/类型检查/测试，关键 E2E，以及存档导出敏感字段扫描。

## 17. 风险与缓解

| 风险 | 影响 | 缓解方式 |
|---|---|---|
| 世界资料规模大且存在语义空白 | 展示内容和生成规则容易被误读 | 第一阶段只抽取角色创建最小资料；建立来源注释、完整性测试和人工校对。 |
| 模型输出数值不稳定 | 同类角色尺度失真 | 硬规则程序计算；输出结构化；补充短期资源标尺；保存提案与裁决差异。 |
| 生成慢且可切档 | 迟到响应串档或覆盖新草稿 | save ID + request ID + revision，任务独立持久化，提交前复核版本。 |
| 自定义模型协议差异 | 思考开关或结构化输出失效 | Provider 适配层与能力检测；不支持时降级并明确提示。 |
| SQLite 被长任务占锁 | 页面操作卡住 | 模型调用完全在事务外，WAL，短写事务，busy timeout。 |
| 存档格式很快演进 | 老存档不可恢复 | 从首版引入 schema/ruleset 版本、导入预检和显式迁移。 |
| API Key 泄漏 | 凭据风险 | 独立凭据存储、只返回掩码、日志脱敏、导出排除和自动测试。 |
| 第一阶段过度预建第二阶段 | 延期且领域模型被猜测污染 | 仅保留版本字段与扩展入口，不创建空壳任务、战斗、记忆系统。 |

## 18. 第一阶段最终验收清单

- [ ] 前端和 Python 后端可按文档在干净环境启动。
- [ ] 角色创建所需世界资料与原始设定经人工校对。
- [ ] 多存档可创建、切换、重命名、删除、导入和导出。
- [ ] 存档 A 生成期间可操作存档 B，任何响应都不会串档。
- [ ] 模型 API 可配置和测试；思考开关按能力正确展示。
- [ ] API Key 不出现在前端读取结果、日志、游戏数据库导出和存档 JSON 中。
- [ ] 13 步角色创建完整，草稿可恢复，设定图位置有一致占位。
- [ ] 种族寿命、阶位称号、地点规则和势力互动机会来自版本化资料。
- [ ] 势力步骤只展示信息与游戏内机会，不保存选择；提示可直接下一步并说明势力在游戏过程中加入。
- [ ] 外貌、性格和天赋预设词已由策划确认并进入版本化资料。
- [ ] 特殊地点对不同种族的生存与访问保障有明确规则。
- [ ] 长期属性范围、短期资源标尺、基础/有效战力、EXP=0 和经验阈值等规则由程序校验。
- [ ] 模型生成失败、超时、坏格式、取消和过期结果均有可恢复体验。
- [ ] 完整角色面板支持接受和带意见重新生成。
- [ ] 接受后正式角色原子入档并进入游戏壳。
- [ ] 导出导入往返一致；坏文件不会产生部分数据。
- [ ] 单元、集成、前端和关键 E2E 测试通过。
- [ ] 游戏壳明确正式 GM 玩法属于第二阶段，没有未完成按钮伪装可用功能。

## 19. 第二阶段接口预留

第一阶段只为以下能力保留稳定接入点：已确认角色、当前地点、存档偏好、规则集版本、状态 revision、模型 Provider 与 `extensions`。第二阶段应在新的需求评审中再设计 GM 回合协议、行动裁决、历史、记忆、故事弧、战斗、经验和地区主线，不以本规划中的占位替代正式领域设计。
